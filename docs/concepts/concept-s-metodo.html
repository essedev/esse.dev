01Architettura prima del codice
Un agente che sa dove sta lavorando sbaglia molto meno.

Dati, confini e standard si decidono prima della prima riga. Il codice arriva dopo, ed è la parte che l'agente fa meglio di me.

  • Dove si vede
  • NexusUn solo motore: da uno schema escono storage, API, tool dell'assistente e interfaccia.
  • ZenoUn motore in Astro e un solo Worker per tutti i siti: pubblicare è caricare un file.
  • Questo sito39 decisioni numerate in docs/DECISIONS.md, nel repo pubblico.
02Il contesto è il lavoro
Una regola scritta in un prompt è una probabilità, la stessa regola in un hook è una garanzia.

Convenzioni, regole e documenti dicono all'agente come lavoro io. Non è un assistente a cui chiedere frammenti, ma un esecutore a cui dare contesto, vincoli e criteri di verifica.

  • Dove si vede
  • Questo sitoCLAUDE.md e tre regole che si caricano per tipo di file, in chiaro nel repo.
  • RelayLo stato di ogni agente arriva dagli hook nativi, non dal parsing dell'output.
  • NexusUn server MCP con OAuth: qualunque coding agent legge e scrive nei miei dati.
03Misurare invece di fidarsi
Prima si misura, poi si decide cosa dire, e una conclusione sbagliata si ritira per iscritto.

Il codice generato sembra giusto anche quando non lo è. Nei miei progetti il perimetro di quello che ho misurato, e di quello che no, è scritto accanto ai risultati.

  • Dove si vede
  • pgbee3.000 reclami veri: 12.000 job, zero falliti, circa 0,14 dollari ogni 1.000 righe.
  • Local LLM Experiments18 su 18 con un modello locale, e il perimetro stretto scritto nel repo.
  • L'agente79 domande di prova per il filtro d'ingresso; token e costo di ogni risposta a schermo.

Un lavoro vero, dall'inizio alla fine: l'agente di questo sito.

La pagina Agente è un agente con tool veri, che mostra ogni chiamata e quanto costa. L'ho costruito così, e ogni passo ha lasciato un file che puoi aprire.

  1. 01
    Architettura prima del codice

    Prima le decisioni, poi una riga

    Un Durable Object per visitatore, limiti espressi in costo reale con un filtro davanti, tool solo in lettura sui repo pubblici. Scritto prima di cominciare, con le alternative scartate.

    docs/DECISIONS.md #11-#14Modello, limiti, tool, sotto-agenti
  2. 02
    Il contesto è il lavoro

    Le regole dell'agente, scritte per l'agente

    Modelli, budget, tool e test hanno una regola che il coding agent carica da solo quando tocca quei file. Non serve ricordarglielo a ogni sessione.

    .claude/rules/agent.mdSi carica sui file dell'agente CLAUDE.mdComandi, convenzioni, cosa non toccare
  3. Il coding agent esegue

    Il codice lo scrive l'agente

    Dentro quei confini il codice è la parte veloce: dal primo commit alla pagina online, con sotto-agenti, errori gestiti e stati del lavoro arrivati nei cicli successivi.

    src/agent/Il codice, pubblico 3 ott 2026Arriva l'agente, nelle modifiche
  4. 03
    Misurare invece di fidarsi

    Numeri prima di aprirlo a tutti

    Il filtro d'ingresso si prova su un set fisso di domande, con le soglie. Il costo si misura su un campione prima di accenderlo, e quello che non ha funzionato resta scritto: i sotto-agenti che parlano fra loro, provati e lasciati fuori.

    79domande in tests/eval/jev-triage.json 0,05-0,1centesimi per una domanda semplice, misurati in preview DECISIONS.md #36Provato e lasciato fuori, per iscritto

Dove gira tutto questo: il mio setup. Un solo contesto per Claude Code, Codex e OpenCode, e hook che fermano un push sull'account sbagliato o un file con un segreto.
